# 决策原则

## 生命周期的职责

需求与工程基础 → 框架与渲染 → 样式与组件 → 状态与数据 → 编译与转换 → 构建与打包 → 规范与质量 → 测试 → 性能 → 发布 → 观测 → 维护。

这是检查遗漏的顺序，不是每一项都需要安装一个库。

- React 是 UI 库；Next.js 在 React 之上增加应用框架能力，二者不是同层替代。
- 编译器处理语法，打包器处理模块图，构建工具提供开发与交付工作流。沿用框架默认构建，不默认组合 Vite + webpack 等双流水线。
- TS 转换不等于类型检查；运行时输入需要独立校验。客户端校验不等于后端权限。
- 客户端状态与远端缓存分开。已有框架的数据层足够时，不必再添加缓存库。
- 先用 CSS、语义 HTML、浏览器 API，复杂行为才增加专用库。

## 关键冲突

- 静态部署只发布资源；SSR、动态 API、服务端共享持久化、私密令牌签发需要外部运行时。本机 IndexedDB 等离线存储不需要后端，但不能代替多用户共享持久化。
- 协同 CRDT 合并不能保证余额、权限等业务不变量；设计同步边界、撤权和存储策略。
- 撤权不能追回已经下载的明文，也不能立即停止断网设备修改本地副本；重连时重新鉴权并拒绝未授权同步。纯白板不默认加入富文本编辑器，先选定图形模型与画布交互。
- WebSocket / Socket.IO 连接不是完整 IM。消息序号、持久化、重连补发、幂等、加密与认证需要协议和后端支持。
- 游戏框架和渲染器不同。2D 关卡与物理需求优先游戏引擎；纯可视化可以选择绘图库。UI 框架状态不是逐帧渲染循环。
- SSR 只选支持服务端环境的包；依赖 window / WebGL 的渲染放客户端生命周期，销毁时释放资源。
- 原生移动、桌面和扩展有独立的构建、权限、签名或审核流程，网页托管不能替代分发。
- 兼容性要核对适配器，不能因为同一库有多框架版本就假定 API 一致。

## 开源与证据

许可证在源码仓库核查，记录具体文件。MIT、Apache-2.0、BSD 等宽松许可与 GPL/AGPL/MPL 等 copyleft 许可的义务不同；不是所有开源许可都能无条件嵌入任何发行方式。重要发布场景按实际分发与服务方式复核义务。

不要推荐仅免费但非开源的产品。可以说明必需的外部能力，但不能把闭源云服务纳入“开源栈”。开源 SDK、商业托管和独立服务器逐项区分。官方能力事实与编辑推荐理由应分开写；目录不承诺供应商的兼容性或性能。
